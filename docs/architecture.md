# Architecture

`ctx` uses a functional core with an imperative shell. Pure decisions depend only on normalized domain values; Git, Tree-sitter, SQLite, CLI, and MCP remain replaceable boundaries.

```text
Git + .context + configured languages
          │
          ▼
   adapters (I/O)
          │ normalized IR / port values
          ▼
      app use cases
          │
          ▼
 core planning, traversal, ranking, review
          │ explicit effects
          ▼
     SQLite adapter
          │
          ├── CLI
          └── MCP
```

## Workspace boundaries

| Crate | Responsibility |
| --- | --- |
| `ctx-core` | Domain types and pure incremental planning, impact, review, context compilation, verification scoring, and schema-change/reconciliation classification |
| `ctx-app` | Narrow ports and use-case orchestration |
| `ctx-adapters` | Git inspection, analyzer registry, Python/Rust/Go Tree-sitter normalization, `.context` parsing, SQLite transactions, GitLab/Jira HTTP clients, and the CLI-based AI-agent subprocess adapters |
| `ctx-cli` | Human and JSON command surface |
| `ctx-mcp` | Thin stdio protocol adapter over the application services |

The core has no dependency on filesystem paths as handles, database row IDs, SQL, Git processes, parser nodes, CLI arguments, or protocol requests. SQLite row IDs never become domain identity.

The CLI composition root owns Clap parsing and top-level dispatch only; verification and federation workflows live in dedicated command modules, while `agent_dispatch::ConfiguredAgent` is the single construction point for Claude Code, Codex, and Antigravity adapters.

## Index transition

1. Git resolves `HEAD`, verifies that configured source is committed, and reports changed paths. `.context`/`.ctx-candidates` inputs get the same check only when their location (possibly redirected via `ctx context-store set`, [ADR-CTX-050](../.context/decisions/external-context-store.yaml)) is itself a Git repository; a plain-directory context store has no commit gate at all.
2. The configured current source set is reconciled with the stored snapshot, covering config-only include/exclude changes.
3. The analyzer registry dispatches each added, modified, or renamed source by extension; its Tree-sitter module emits a complete language-neutral `FileAnalysis`, including supported static database interactions.
4. The pure incremental planner matches identities conservatively and emits node writes, retirements, structural/data-fact invalidation and rebuild, and semantic-staleness effects.
5. SQLite applies the plan and commit marker in one transaction; business documents and explicit claims are synchronized in a second bounded transaction.

Repeated indexing at the same commit performs no source parsing. Changed source bodies mark attached non-fact claims stale. Structural facts owned by the analyzer are closed and rebuilt; semantic assertions are never silently recreated as facts.

Re-indexing alone never heals a stale semantic claim, by the same principle. `ctx verify --stale [--agent <claude|codex|antigravity>]` (`REQ-VERIFY-004`) is the one path that can: it runs every currently stale claim (`ctx_core::verification::stale_semantic_claim_details`) through an independent agent review — a third sibling to `SemanticAgent`/`KnowledgeReviewAgent` (`ADR-AGENT-001`), `ctx_app::ports::StaleClaimReviewAgent` — with the product intent's statement and the current code of whichever side is a symbol both inlined into a self-contained prompt (`ctx_adapters::agent_contract::review_stale_claims`), never relying on the agent to read files itself. An `accept` verdict is binding: `ctx_app::ports::StaleClaimStore::reactivate_stale_claim` reactivates precisely the one edge identified by its fingerprint, never the whole document that happens to declare it. A `reject` verdict is never applied automatically — only ever printed as a suggestion with the agent's reasoning, since discarding a hand-authored mapping silently is a materially different risk than confirming one still holds.

Each persisted file records its analyzer normalization version. If an upgraded module changes extraction or call-resolution semantics, version reconciliation schedules affected files for reparse even when Git bytes and `HEAD` are unchanged. A true same-commit no-op is returned only after source scope and analyzer versions are current.

## Identity and validity

Stable keys are derived from repository-relative file paths, language-qualified canonical symbols, or human-owned business IDs. Symbol matching never crosses a language boundary and tries, in order:

1. the same canonical path;
2. a unique name/signature match in the prior file;
3. a unique structural fingerprint.

Ambiguity creates a new identity instead of conflating two symbols. Versions are valid from one commit until a later transition closes them. An active relationship may still be marked stale when its input fingerprint changed; queries surface that uncertainty instead of hiding it.

Stable symbol keys have the form `symbol:<language>:<canonical-path>:<kind>`. Human-authored mappings may use the shorter canonical path when it is unique or the complete stable key to disambiguate equal paths across languages. Static call resolution is likewise language-scoped.

## Language modules

`AnalyzerRegistry` is the only analyzer passed to indexing and review. It owns independent self-describing `AnalyzerModule` implementations and routes by source extension. Git filtering uses the same supported-language declarations, so configured discovery and parser dispatch cannot disagree.

Python, Rust, and Go are built in today. A future TypeScript, Java, or Zig adapter supplies parser-specific extraction but must return the common IR: complete-file hash, symbol kind/name/canonical path, version range, signature, body hash, whitespace-insensitive structural fingerprint, simple call sites, and normalized interactions it can prove. Parser syntax types remain inside `ctx-adapters`; application and core crates stay unchanged. Duplicate module names or extension claims are rejected when the registry is built.

Rust canonical paths use `crate` for a root `src/` tree and the workspace crate directory for `crates/<name>/src/`. Inline modules and implemented types extend that namespace. Trait-implementation methods additionally include the complete trait name (including generic arguments), so legal pairs such as `impl From<u8>` and `impl From<u16>` cannot collide. Syntax-error trees are rejected rather than partially indexed.

Go canonical paths are directory-based rather than file-based, matching Go's one-package-per-directory convention: every `.go` file in a directory shares that directory's package namespace regardless of its declared `package` clause, and a root-level file with no directory falls back to `main`. Methods are namespaced under their receiver's innermost named type (pointer and generic receivers unwrap to that name). Interfaces map to the shared `Trait` symbol kind; defined/alias types that are not `struct`/`interface` map to `TypeAlias`. `const`/`var` blocks emit one symbol per bound identifier. Go raw (backtick) string literals reuse the same static-SQL-literal recognizer as Python/Rust since they cannot contain escapes or interpolation. Syntax-error trees are rejected rather than partially indexed, matching the other modules.

## Static database interactions

Language adapters inspect only recognized execution calls and macros. A shared deterministic SQL recognizer extracts normalized entity identifiers from common static `SELECT ... FROM/JOIN`, `INSERT INTO`, `UPDATE`, `DELETE FROM`, and `MERGE INTO/USING` forms. Interpolated/dynamic SQL and unsupported syntax produce no fact.

The normalized IR attaches typed reads/writes to their owning symbol. Write accesses additionally carry specific column names when the SQL form reliably identifies them — an `UPDATE ... SET` clause's assignment targets, or an `INSERT`/`MERGE` statement's explicit column list — extracted by a separate raw-text scanner (`write_columns`) reusing the DDL parser's comma/paren-aware primitives, since the shared entity tokenizer intentionally does not preserve that structure. `DELETE`, a bare `INSERT ... VALUES` with no column list, and every `SELECT`/read form stay column-empty rather than guess (attributing `SELECT` columns to tables across joins without a real parser is not a recognizer's job).

The core planner derives repository-scoped `DbEntity` nodes and `READS_FROM`/`WRITES_TO` `FACT` edges, deduplicates repeated accesses, retires entities after the last current access disappears, and gives every edge a static-analysis producer, commit boundary, source file, a line/column evidence locator (`lines:4,5 columns:paid_until,status`), and statement fingerprint. Analyzer-version bumps force a same-commit reparse when extraction semantics change.

Impact and Context Pack treat a direct data interaction as one bounded structural hop and report database entities separately from implementation. A `table.column` impact seed (see "Column-level impact seeds" below) narrows to that column's specific readers/writers using this evidence. Review compares before/after access sets and reports a concrete database-read/write change signal; it does not claim the related product contract is violated. Verification scoring can use a shared database interaction as one explained signal, never as an assertion by itself.

## HTTP API contracts

Alongside the shared SQL recognizer, the Python adapter recognizes FastAPI/Flask endpoint declarations and `requests`/`httpx` outbound calls into the same normalized IR family (`ApiEndpoint`, `ExternalCall` in `ctx-core::ir`), attached to their owning symbol exactly like a database access. A recognized endpoint becomes an `EXPOSES` `FACT` edge to an `ApiEndpoint`-attributed node; a recognized outbound call becomes a `CALLS_EXTERNAL` `FACT` edge. Path/query/body parameter classification is a static heuristic (path-segment name match, then a request-body-type-hint check, then query as the default); `Request`-typed and `Depends(...)` parameters are excluded rather than misclassified. A dynamically constructed route or call URL yields no fact, matching the project's static-SQL-literal rule of never guessing from a runtime expression. See [docs/api-contracts.md](api-contracts.md) for worked examples.

`ctx-core::review::diff_api_endpoints` classifies before/after HTTP contract changes (`ApiChangeKind::Added`/`Removed`/`ContractModified`) as destructive or routine, surfaced by `ctx review` as `ReviewReport.api_findings` — structurally separate from `findings` and `schema_findings`, with the same bounded advisory intent/test neighborhood convention schema findings use.

## Schema migrations

A `goose` (<https://github.com/pressly/goose>) module is registered beside the language analyzers, dispatching on the `.sql` extension. It reads only a migration file's `-- +goose Up` section (`-- +goose Down` describes how a change is reverted, not what is currently declared) and recognizes `CREATE TABLE` (including table-level `PRIMARY KEY`/`UNIQUE`/`FOREIGN KEY`/`CHECK`), `ALTER TABLE ... ADD/DROP/RENAME COLUMN`, `ALTER TABLE ... RENAME TO`, `ALTER TABLE ... ALTER COLUMN ... TYPE`/`SET-DROP NOT NULL`/`SET-DROP DEFAULT`, `DROP TABLE`, and `CREATE`/`DROP INDEX` with a dedicated deterministic DDL reader (`ctx-adapters::database::parse_ddl_statement`) — not a SQL dialect parser and not Tree-sitter-based, so its edges carry the `goose_ddl_recognizer` producer rather than the `<language>_tree_sitter` convention every grammar-backed module uses. `ALTER TABLE ... ADD/DROP CONSTRAINT` stays unsupported: without the table's already-declared columns there is no reliable way to know which columns a bare constraint name refers to. A file with no goose annotations, or no recognizable DDL, yields zero symbols instead of an error or a guess.

Each migration file becomes one `SchemaMigration`-kind symbol (canonical path derived from its path, for example `migrations.20240101000000_create_subscriptions`) carrying zero or more declared `SchemaTableDefinition`s. This reuses the existing per-file commit-bounded versioning, identity, and retirement machinery symbols already have — a migration is not a new kind of storage concept, just a new symbol kind and a new `DEFINES_SCHEMA` `FACT` edge kind alongside `READS_FROM`/`WRITES_TO`, pointing at the same `DbEntity` graph those statically-recognized SQL accesses use. A table declared only by a migration, never read or written by any indexed code, still becomes a `DbEntity` and appears in impact/review/Context Pack like any other data contract.

`SchemaTableDefinition`/`SchemaColumn` (`ctx-core::ir`) is the language/framework-neutral persistent-state IR every schema source populates identically; core code never imports a goose or `SQLAlchemy` concept. Each `SchemaColumn` carries `nullable`/`primary_key`/`unique`/`foreign_key`/`default` when a recognizer can statically determine them (`None`/`false` means "not statically determined", never "proven absent"). A `SchemaTableDefinition` can describe additive state (`columns`, a `CREATE TABLE`'s initial set or an `ADD COLUMN`'s additions, distinguished by `table_created`) and/or removal/rename operations (`dropped_columns`, `renamed_columns`, `column_alterations` for a standalone `ALTER COLUMN` clause that only knows the new value not the old one, `table_dropped`, `renamed_from`, `indexes_added`/`indexes_dropped`) in the same value, since one real `ALTER TABLE` statement can combine several. Column/constraint evidence rides the existing `evidence_locator` mechanism, so `ctx explain` renders it (`columns:name:type,...` for schema edges) without new query surface. `ctx` deliberately does not merge multiple migrations' declarations for the same table into one *stored* "current" schema (that would require a dialect-complete parser and an Alembic/goose-version-graph-aware resolver); each migration file's declaration remains its own fact with its own evidence. A best-effort ordered replay (file-path order) exists only as an ORM-reconciliation diagnostic — see below — never as a stored fact or a `DbEntity`'s answer to "what are this table's current columns".

The Python module recognizes `SQLAlchemy` declarative models with the same `DEFINES_SCHEMA`/`SchemaTableDefinition`-shaped fact (a class is the versioned unit instead of a migration file, and is always `table_created: true` since a declarative model is a complete declaration, not an incremental change). Only a class that assigns a static string literal to `__tablename__` — the framework-mandated declarative-mapping marker — is treated as a model at all; declarative-base detection (resolving `class X(Base):`) is deliberately not attempted, since aliasing and inheritance make it unreliable without import resolution, while `__tablename__` is unambiguous. Within a recognized model, `name = Column(...)`/`name = mapped_column(...)` attribute assignments become columns: the type is read from the constructor's first positional argument (or the variable's type annotation, for the annotation-only `Mapped[int]` style, or `"unknown"` if neither is present) — not a SQLAlchemy type-system parser — and `nullable=`/`primary_key=`/`unique=`/`default=`/`server_default=`/`ForeignKey("table.column")` (positional or nested in a keyword argument's value) populate the same constraint fields goose's DDL reader populates. A dynamic `__tablename__` (anything other than a plain string literal) makes the whole class unrecognized, matching the project's static-SQL-literal rule of never guessing from dynamic expressions — this is this system's only "ambiguous ORM mapping" case, since identity is otherwise always exact-string, never fuzzy.

## Schema-aware review

`ctx-core::schema` is a pure module reading only the shared `SchemaTableDefinition`/`SchemaColumn` IR (no goose/`SQLAlchemy` concepts), providing two classification views. `declared_schema_changes` reads what one schema-declaring statement/file declares about its own table, independent of history — a brand-new migration that drops a column is destructive the moment it exists, with no prior version needed to know that; `SchemaMigration` symbols always use this view, since goose migrations are historical, append-only records where what a statement declares is what matters. `diff_schema_tables` structurally compares two versions of the *same* schema-declaring symbol (an edited `SQLAlchemy` model, matched by canonical path within one changed file) column by column; renames are never inferred from a diff — a column missing from `after` and a new column present in `after` are reported independently as dropped/added unless the source explicitly declares the rename. Each `SchemaChange` carries a `destructive: bool` per the contract-relevant list (column/table dropped or renamed, nullable tightened, type changed, FK/unique changed, a new `NOT NULL` column with no `DEFAULT` added to an already-existing table) versus routine/additive evolution (a new nullable column, a new index, a relaxed constraint).

`ctx review` surfaces these as `ReviewReport.schema_findings`, kept structurally separate from `findings`: an *observed deterministic schema change* is never conflated with a *proven requirement violation*. Each `SchemaFinding` also carries a bounded, one-hop-then-one-hop advisory neighborhood (`db_entity_neighborhood` in `review.rs`) — the affected table's directly connected code (via `ReadsFrom`/`WritesTo`/`DefinesSchema`), and that code's own mapped `Implements`/`Enforces`/`Satisfies`/`CoveredBy` edges — so a destructive change to a mapped table can point at the requirement/invariant/tests it likely affects without a fuller traversal that could bridge a popular table into unrelated product areas. An empty `related_intents` means no known product mapping was found, not that the change is unrelated.

## ORM/migration reconciliation

`ctx-core::schema::reconcile_orm_and_migrations` compares a `SQLAlchemy` model's declared columns against a migration-derived column set, for entities declared by *both* sources only — an entity known from only one source has nothing to reconcile, and this system never fuzzy-matches schema identity (a migration's and an ORM model's `entity` name are either the same string or unrelated facts about different tables), so there is no "ambiguous match" state to represent. It operates directly on the current `GraphSnapshot` (every `Symbol` node's `PlannedNodeAttributes` already carries its full `schema_tables`, since node attributes round-trip through SQLite as JSON), dispatching migration versus ORM purely by `symbol_kind`. The migration-derived column set replays every migration touching that entity in file-path order (goose's own numeric-timestamp-prefix convention), applying declared add/drop/rename operations in sequence — a diagnostic reconstruction only, never persisted as a fact. `ctx status` folds any divergence into its existing `NeedsAttention` health state (alongside stale semantic edges) as `StatusReport.schema_divergences`, presence-only (it does not compare types/nullability between the two sources).

## Column-level impact seeds

`ctx impact table.column` (for example `subscriptions.paid_until`) does not add a column-level graph node — that would be new ontology for a single query shape. Instead `resolve_table_column_seed` in `impact.rs` recognizes the pattern, and when `table` resolves to exactly one `DbEntity` (an exact literal match is always tried first, so a real identifier that happens to contain a dot is never misparsed), the seed resolves to that same `DbEntity` node a bare table query already resolves to. `focus_on_column` then narrows `ImpactReport.implementation` to the specific readers/writers whose `ReadsFrom`/`WritesTo`/`DefinesSchema` evidence names that column, using the column evidence static write extraction populates; `data_contracts`/`requirements`/`invariants`/`tests` stay table-level, since only `implementation` has direct per-symbol column evidence to filter on. A column absent from every collected evidence for that table (a typo, or a form this codebase's static recognizers cannot see) does not silently look identical to "this column has no readers": table-level impact is left intact plus an explicit `ImpactUncertainty` explaining why.

## Claims and provenance

Every edge is classified as one of:

- `FACT`: deterministic static structure such as containment or a uniquely resolved call;
- `ASSERTION`: explicit documentation or a separately recorded human acceptance;
- `INFERENCE`: a heuristic candidate with its derivation signals.

Evidence records source kind, URI, locator, commit, author/timestamp when relevant, and strength. Accepting an inference preserves the original inference and creates a distinct human assertion. Rejecting it preserves a rejected record so the same fingerprint is not repeatedly proposed.

## Query policies

Impact and Context Pack traversal are bounded and typed. Structural adjacency is limited to the seed neighborhood, semantic expansion is capped, rejected claims are excluded, and an inferred edge cannot recursively amplify another inference. Deterministic ordering is used throughout user-visible output.

Context compilation reserves budget for evidence and prioritizes invariants and requirements before implementation, tests, direct data contracts, adjacency, and low-confidence material. Its token estimate is deliberately conservative and never reports a pack above the requested limit.

Review compares normalized symbols before and after a Git diff, classifies the change, then joins only strong implementation claims to product intent and linked tests. Non-behavioral changes are suppressed by default. A finding is rendered from stored claims and evidence; the reviewer-facing rationale is not generated by an LLM.

`ctx explain <symbol>` additionally attaches that symbol's artifact history — every commit, merge/pull request, or comment whose changeset structurally touched or discussed it (`ctx-core::neighborhood::artifact_history`), newest first — when the query resolves to exactly one `CodeSymbol` subject. Assembled at the `ctx-app::query::QueryService` layer alongside `knowledge_provenance`, since artifacts and their links live outside the graph; empty for a relationship query, several matches, or a non-code subject.

## External artifacts and AI-assisted knowledge extraction

`ctx ingest <git|code-comments|gitlab|jira>` reads development artifacts — commit messages, branch names, code comments/docstrings, GitLab issues/merge requests/comments/commits, and referenced Jira Cloud issues/comments — through source ports and normalizes each into `ctx-core::artifact::Artifact`, stored in its own tables (`artifacts`, `artifact_links`), never as a `ctx-core::domain::Node`. Network connectors implement the same `ExternalArtifactSource` port and return one `ExternalArtifactBatch`; provider-specific authentication, request modes and normalization remain adapter concerns. An artifact has no place in `ctx impact`/`ctx context` traversal and never automatically becomes a `Feature`/`Requirement`/`Invariant`/`Decision`; it is source material other passes may derive candidates from. `ctx-core::linking::extract_references` deterministically finds ticket-key/issue/MR references in artifact text and links them to already-known artifacts — never a guessed relationship, and never using AI. Each branch other than the repository's resolved default branch is additionally linked (`ContainsCommit`) to the commits it alone contains, and a GitLab merge request is linked (`References`) to its own `source_branch` as a Git branch identity — a structured-field fact, not a text mention. Each commit is linked (`ChangedSymbol`) to every currently indexed code symbol in the files it changed, read from the same `git log` pass rather than a per-commit subprocess; a changeset wider than 10% of the repository's currently indexed files (floored at 20 for small repositories) attributes no symbols at all rather than an arbitrary subset, so the cap scales with repository size instead of a fixed file count. GitLab ingestion stores a per-`(repository, provider)` sync cursor (`ingest_cursors`) so a later run asks for only what changed; Jira instead derives a bounded key set from already-known artifact text and expands provider-reported relationships by one hop. Both HTTP adapters fully paginate their collections and share bounded `Retry-After`-aware retry policy; neither pagination nor retry changes the idempotent artifact identity contract.

`ctx enrich --agent <name>` calls an LLM only when explicitly run. `ctx-core::neighborhood::build_neighborhood` assembles one artifact's bounded, one-hop-only context (its own linked artifacts, the code it touched, nearby tests, and already-mapped product knowledge) — never the whole repository or artifact backlog. Links are read in either direction, since a link is stored by whichever side structurally authored it (a comment records `Comment → Ticket`, a merge request records `MergeRequest → Commit`), so a ticket's own comments and a commit's own containing MR are both part of its neighborhood. Because of that, `ctx-app::enrich::EnrichRunner` never spends its own agent call on a Comment/ReviewComment/Commit/Branch that already structurally resolves to a known parent (a comment's `CommentsOn` issue/MR, a commit's `ContainsCommit` branch/MR, a branch's `source_branch` `References` merge/pull request) — its text is already inside that parent's own neighborhood, so a separate call would mostly repeat it; an orphaned artifact with no known parent yet is still analyzed on its own. `ctx-app::ports::SemanticAgent` is the only boundary `ctx-core`/`ctx-app` know: neither ever names a vendor or model. Each concrete agent (`ctx-adapters::claude_code`, `::codex`, `::antigravity`) is a thin subprocess transport (`claude -p`, `codex exec`, `agy -p`) delegating into `ctx-adapters::agent_contract`, which owns the shared prompt/JSON-response contracts every vendor is validated against identically. CLI vendor selection is centralized in one `ConfiguredAgent` composition point for enrich, knowledge review, and stale-claim review. Every evidence citation and implementation/test-candidate path is checked against the neighborhood the agent actually received, and anything outside it — or malformed output altogether — is dropped or rejected, never trusted. `verify --stale` additionally partitions claims into independently validated prompts capped by both claim count and byte budget, so neither OS argument limits nor one malformed large response can discard an unbounded repository-wide batch.

An `AgentOutcome::Relevant` result is persisted as a `pending` `KnowledgeCandidate` file under `.ctx-candidates/`, with the SQLite `artifact_analysis` ledger recording each artifact's last-analyzed content hash so unchanged content is never re-sent to the agent. It stays `INFERENCE` until `ctx verify --knowledge --accept --id <ID>` writes it as an ordinary `.context/*.yaml` document through the same `BusinessContextReader`/`ContextImporter` path a hand-authored file uses — no second, parallel truth store. Accepting checks a lexical term-overlap similarity against already-active documents of the same kind first and refuses without `--force` when one looks like a likely restatement. The candidate file keeps full agent provenance and the verification decision so `ctx explain` can render the complete artifact → agent-inference → verification chain.

## Federation

`ctx-adapters::federation` lets one repository share a bounded, explicitly-opted-in slice of its product knowledge with sibling repositories checked out locally on the same machine — never a remote fetch. `ctx export` requires `[service].name` in `.ctx/config.toml` and an index current with `HEAD`; it writes a deterministic, commit-labelled `ExportManifest` containing only `visibility: public` business documents and every currently indexed `ApiEndpoint` (an endpoint is structural fact, not a business document, so it isn't gated by document visibility). `NeighborRegistry` (`.ctx/registry.toml`, local and never committed) records neighbors by absolute filesystem path. `ctx sync` re-invokes each neighbor's own `ctx` binary to refresh its export, then calls `matching_resolutions` to resolve this repository's `CALLS_EXTERNAL` facts against the neighbor's exported endpoints by HTTP method and normalized path template, recording each match as `FEDERATED_MATCH` — never `FACT`, since its truth depends on two independent commits rather than one — and reporting every unmatched call honestly instead of guessing. See [ADR-FEDERATION-002](../.context/decisions/federation-storage-boundary.yaml) for the storage-boundary decision and [docs/federation.md](federation.md) for the workflow.

Synchronized neighbor data lives in its own `federated_syncs`/`federated_documents`/`federated_endpoints`/`federated_external_call_resolutions` tables and never creates a local `Node` or `Edge` — ordinary indexing, impact, explain, and review never read it. A schema-version mismatch or an exported `service_name` that doesn't match the registered neighbor name is rejected rather than imported. `ctx sync` continues past a failing neighbor instead of aborting the whole run, and replaces each successful neighbor's snapshot atomically.

`ctx trace` ([ADR-FEDERATION-003](../.context/decisions/federated-trace-traversal.yaml)) walks the same structural sequence one `FEDERATED_MATCH` hop describes, repeatedly: `ctx-core::trace::trace_endpoint` follows one endpoint's `Exposes` handler, that handler's `ReadsFrom`/`WritesTo`/`CallsExternal` edges, and hands each outbound call to a caller-supplied `FederationResolver` — the one boundary `ctx-core` knows about federation through, so the traversal and its bounds (8 service transitions, 50 nodes, 16 branches, a `(service, commit, method, path)` visited set) stay unit-testable with a fake resolver. `ctx-cli`'s concrete resolver matches a call against every registered neighbor's already-synchronized manifest (never a live fetch/index/sync) and, on a fresh-enough match, continues by invoking that neighbor's own `ctx trace` as a subprocess in its own checkout with the remaining budget and visited set passed as an internal `--federation-continuation` argument — so only that neighbor's own process ever decides what of its graph is traceable, mirroring how `ctx sync` already delegates its own export to a neighbor's own binary rather than reading its files directly.

## Storage and operations

SQLite runs locally with foreign keys, WAL mode, idempotent migrations, and transactional batch writes. The schema separates repositories, commits, stable nodes, node versions, claims/edges, sources, evidence, annotations, aliases, derivations, external artifacts and links, the per-artifact analysis ledger, per-provider ingest cursors, and synchronized-neighbor tables (`federated_syncs`, `federated_documents`, `federated_endpoints`, `federated_external_call_resolutions`). Pending/decided knowledge candidates live as YAML files in `.ctx-candidates/`, not in a removed `knowledge_candidates` table. The database and its WAL files remain repository-local private state under `.ctx/`.

Source code is never sent to a network service by the deterministic core. Network-backed work happens only when explicitly requested: `ctx ingest gitlab` calls GitLab's REST API (an optional `CTX_GITLAB_TOKEN`, never committed), `ctx ingest jira` calls Jira Cloud REST v3 (credentials only from `CTX_JIRA_EMAIL`/`CTX_JIRA_TOKEN`), and `ctx enrich`/agent-driven `ctx verify` invoke a locally installed agent CLI that owns its own authentication. None runs as a side effect of indexing, impact, explain, or review. Federation reads local sibling checkouts/manifests and is not itself a remote registry or network client. MCP tools are read-only and use the same query/review services as the CLI.

Status health is assembled in `ctx-app` from Git freshness, the effective source scope, current typed node counts, epistemic relationship counts, and staleness. This keeps health classification out of terminal rendering and prevents a large structural graph with no product assertions from being labelled ready.
