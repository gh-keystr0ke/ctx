## 2026-08-18 — Hardening: a real panic-safety gap in the new DDL recognizer

- Audited every new hand-rolled byte-slicing function added for the goose/SQLAlchemy milestones (`database.rs`'s `ddl_table_columns` and its helpers) for UTF-8 char-boundary panics, since these operate on arbitrary user-authored SQL/migration text rather than the whitespace-only ASCII the rest of the codebase's tokenizers assume. Reasoned through every raw index/slice: ASCII-keyword byte-offset arithmetic is boundary-safe when the offset is derived from a matched all-ASCII run (`find_whole_word`, `find_keyword_pair`, quote-delimited identifiers), and `char`-based `str::find`/`trim_start` calls are boundary-safe by construction.
- Found one real gap: `strip_word_ci` sliced `trimmed[..word.len()]` directly. `word` is always a plain ASCII keyword, but `trimmed` is arbitrary UTF-8 content (a column/table name, comment, or unrelated text near where `ADD`/`COLUMN`/`IF`/`NOT`/`EXISTS` are checked); if a multi-byte character happens to straddle byte offset `word.len()`, the panicking `[..]` index would crash the whole `ctx index` run on merely malformed-looking (non-ASCII, not otherwise invalid) migration content. Fixed by switching to `trimmed.get(..word.len())?`, which fails the match gracefully instead of panicking — consistent with the recognizer's existing "unrecognized syntax yields no fact, never a guess or a crash" contract.
- Added a targeted regression (`ddl_table_columns_never_panics_on_multi_byte_utf8_near_a_keyword_boundary`) using a real 3-byte CJK character positioned at the exact byte offset that reproduces the boundary violation, confirmed by the same reasoning that identified the bug (not by trial and error): one case exercises the `ALTER TABLE ... ADD` path, one the `CREATE TABLE ... IF NOT EXISTS` path (both previously reachable panics), plus a positive case proving a non-ASCII column name is still handled correctly end-to-end since `first_word`/`unquote_identifier`'s `char`-based paths were already safe.

## 2026-08-18 — Hardening: dogfooding this repository's own accumulated diff found a real identity-collision bug

- The release gate protocol calls for re-indexing this repository at `HEAD` before declaring anything done. Since the four commits so far in this session hadn't been indexed yet, this was the first `ctx index` to process Go/goose/SQLAlchemy work together with everything untouched since `d13888a`, in one transition — and it failed: `"index plan contains more than one write for stable key 'symbol:rust:ctx_adapters.python.structural_fingerprint:Function'"`. The pre-storage duplicate-write guard from an earlier milestone (`normalize_plan`) caught it and rolled back cleanly; no corrupt state was written. Worth stating plainly: this was a real, previously-latent defect in `plan_incremental_index`, not a fixture or test artifact, and it surfaced only because of dogfooding on real accumulated history.
- Root cause, traced through `match_symbols`'s three tiers plus the `used` set (not guessed): `go.rs`'s and `rust.rs`'s trivial `structural_fingerprint` helpers are byte-identical (`hash_bytes(&normalized)`); separately, `goose.rs`'s and `python.rs`'s are byte-identical to *each other* (`blake3::hash(&normalized).to_hex().to_string()`) — an artifact of copying the established per-file-duplicated-helper convention into two new files without varying the trivial implementation. `used` is correctly shared and checked across the whole transition, but it is only *populated* as each file is processed in `changes`' order. When `go.rs` (a brand-new file with no history of its own) was processed *before* `rust.rs` (unchanged, but present in `changes` because other functions in the same file changed), `go.rs`'s tier-3 same-shape fallback found `rust.rs`'s own historical identity unclaimed and took it. When `rust.rs` was processed next, its rightful tier-1 exact-canonical-path match was excluded because that key was now `used` — every tier fell through, and the final `symbol_key()` fallback deterministically recomputed that exact same already-claimed key (it's derived purely from `rust.rs`'s own canonical path, unaffected by what `go.rs` had done), producing two writes for one stable key. Correctness depended on `changes`' processing order, which is not a property the domain promises anywhere.
- Fixed by adding a reservation pre-pass to `plan_incremental_index`: before any file's `match_symbols` fallback tiers run, every changed file's definitions are checked for an exact, unique historical canonical-path match, and those keys are claimed into `used` first — across the *whole* transition, not per file. This guarantees a symbol whose canonical path is genuinely unchanged always keeps its own identity no matter what order `changes` lists files in, so a same-shape coincidence in an unrelated new file can never preempt it. Factored the shared tier-1 predicate into `exact_canonical_match` so the reservation pass and `match_symbols` use identical logic instead of two hand-kept-in-sync copies.
- Added `same_named_same_shaped_symbols_claim_distinct_identities_regardless_of_file_order`, the mirror image of the existing (order-dependent, previously order-*lucky*) `same_named_same_shaped_symbols_in_different_files_claim_distinct_identities` regression, with the file order reversed. Verified methodologically, not just by inspection: temporarily gated the new reservation pass behind an env var, confirmed the new test reproduces the *exact* `DuplicateNodeWrite` error dogfooding hit, then removed the gate and confirmed it passes.
- This is the same defect *class* (the cross-file structural-fingerprint-fallback family) this project has hit and fixed twice before per this file's own history ("Trait implementation identity found by dogfooding", "Historical matching isolated from the current transition"); each prior fix narrowed the fallback's blast radius (requiring name equality, splitting historical/current snapshots) but none made the outcome order-independent, which is what actually broke this time. Left both regressions in place since they cover genuinely different orderings of the same scenario.

## 2026-08-21 — Phase 4: bounded artifact-neighborhood assembly

New pure `ctx_core::neighborhood` (no `.context` doc: pure internal assembly with no CLI surface of its own yet, feeding Phase 5's agent boundary): `build_neighborhood(subject, links, known_artifacts, graph)` follows the same one-hop-only discipline `ctx_core::impact`/`ctx_core::context_pack` already enforce against neighborhood leakage — every lookup is a single, direct hop over `subject`'s own `ArtifactLink`s and the graph edges touching the resulting changed-symbol set, never a recursive/semantic expansion. ## 2026-08-23 — `ctx verify --knowledge --auto`: the feature itself

Third and final piece of the user's original request, landing everything `decision_method` (previous entry) and candidate clustering (previous entry) were built for: `ctx verify --knowledge --auto --agent <claude|codex|antigravity> [--model <model>] --id-prefix <PREFIX>` reviews and decides every pending candidate through an agent instead of a human pressing accept/reject hundreds of times. Before writing this, confirmed one more open design question with the user via `AskUserQuestion` -- REQ-VERIFY-002 guarantees a document's stable ID is only ever human-typed, never guessed from content, and `--auto` has no human typing one per candidate by construction, so something has to allocate IDs. Offered three options; the user picked "require `--id-prefix` and auto-number under it" over a fully content-derived slug or having the review agent itself propose names.

**ID allocation** (`ctx_core::business::BusinessKind::id_stem` + new `ctx_core::verification::KnowledgeIdAllocator`): every accepted document gets `<kind stem>-<prefix>-<NNN>` (`REQ-SUB-001`, `INV-SUB-001`, ...), matching this repository's own existing ID shape. The allocator tracks used IDs from the graph *and* updates itself after every allocation within one run, so a single `--auto` invocation writing several documents never collides with itself, not only with what existed before the run started -- REQ-VERIFY-002's "no ID ever guessed from content" guarantee still holds, just satisfied by a human-supplied prefix instead of a full human-typed ID per candidate, since typing one per candidate is exactly the six-hour cost this feature exists to remove.

**Review contract** (`ctx_core::knowledge::{ReviewVerdict, CandidateReviewDecision, ClusterReview}`, `ctx_app::ports::KnowledgeReviewAgent`, `ctx_adapters::agent_contract::review()`): a deliberate sibling to the existing extraction contract, not a reuse of it -- "does this neighborhood state new knowledge" and "should this already-extracted candidate be accepted" are genuinely different questions with different input/output shapes. `review()` sends one cluster's candidates (fingerprint, kind, statement, evidence excerpts) and asks for a verdict on every one, plus an optional `merged_statement` only when the agent judges two or more accepted candidates to genuinely restate the same knowledge -- clustering is a lexical hint about what to review together, never itself a merge decision. Malformed output is rejected the same way extraction already rejects it: an invented fingerprint, a duplicate decision, or a decisions list that doesn't cover every input candidate exactly once all fail outright rather than being guessed at. Confirmed real independent review, not rubber-stamping, with a dedicated test asserting the agent can reject a candidate extraction already called relevant.

Each vendor (`claude_code`/`codex`/`antigravity`) gained a one-method `KnowledgeReviewAgent` impl delegating to its already-owned `AgentTransport` -- zero new process-invocation code, confirming `ADR-AGENT-001`'s own "a new capability costs only a thin delegation" property a second time.

**Orchestration** (`ctx_app::verification::KnowledgeVerificationService::auto` + `AutoVerifyReport`): loads pending candidates, clusters them, reviews each cluster, then for accepted candidates either writes one merged document (when the agent supplied `merged_statement` for 2+ accepted candidates in a cluster, with every accepted candidate's decision pointing at that same document ID -- extending REQ-VERIFY-002's "original candidate row survives acceptance, pointing at the resulting document" to a many-to-one shape) or one document per candidate otherwise, reusing the exact `candidate_to_document`/`write_document`/`record_decision` path `accept` already uses so an auto-written document is indistinguishable in shape from a human-written one. Every recorded decision carries `DecisionMethod::Agent`, never `Human`. The existing duplicate check (REQ-INCR-002) still runs before every write, unless `--force`; a duplicate is left pending rather than force-created, so a human can still review it through the ordinary interactive flow afterward.

CLI: `ctx verify --knowledge --auto --agent <name> [--model <model>] --id-prefix <PREFIX> [--force]`, clap-enforced (`requires_all`) so `--auto` cannot run without `--knowledge` and `--id-prefix`. Also wired `--model` into plain `ctx enrich` while touching this dispatch code (previously always `None` despite every agent constructor already accepting it) -- a small, low-risk pass-through that was already flagged as open from the first `decision_method` entry.

Four new `ctx-app` tests with a fake review agent (single accept, reject, two-candidate merge into one document, duplicate-skip-then-force) plus four `agent_contract` tests, two `KnowledgeIdAllocator` tests, and one full e2e case (`verify_knowledge_auto_reviews_and_accepts_with_an_honest_agent_decision_method`) using one fake `claude` script that plays both the extraction and review roles across the two calls the test makes, telling them apart by system-prompt content the same way a human skimming stdin would. New `.context/requirements/knowledge-candidate-auto-verification.yaml` (`REQ-VERIFY-003`) and a revalidation of `.context/decisions/interchangeable-semantic-agent.yaml` (`ADR-AGENT-001`) documenting `KnowledgeReviewAgent` as the deliberate sibling trait it is. `cargo fmt --all -- --check`, strict locked-lint `cargo clippy --workspace --all-targets`, and `cargo test --workspace` all green (`ctx-core` 99→101, `ctx-app` 21→25, `ctx-adapters` 73→77, CLI e2e 13→14) before commit.

## 2026-08-23 — `--auto` no longer aborts an entire run on one stale-index ID collision

Same real user, same real `ctx verify --knowledge --auto --id-prefix ML` run against another repository, hit a second issue immediately after the progress-output fix: on cluster 1 of 715, the whole run failed with `error: verification candidates could not be loaded: a business context document already exists at '.../adr-ml-001.yaml'` -- a misleading message (candidates loaded fine; a *write* failed) that also killed 714 still-unreviewed clusters over one bad ID.

## 2026-08-28 — `ctx context-store`: `.context/`/`.ctx-candidates/` may live outside the checkout
